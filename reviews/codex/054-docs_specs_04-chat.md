1. **[high] Tool toggles do not define an enforceable permission boundary.**  
   **Reference:** Behavior rules: “always behind the approval policy in 12”; Context panel: selected project “sets `cwd` for CLI-backed models.”  
   **Why it matters:** A working directory does not restrict filesystem access. The official CLI runners in 01/03 may also have their own tools, outside the daemon’s advertised tool set. Hiding Files or Web in this UI would not necessarily disable those capabilities.  
   **Concrete fix:** Require adapters to enforce the selected tool allowlist, project boundaries, and approval policy across native CLI tools too. Disable tool-enabled chat for adapters that cannot enforce them. Show effective permissions before sending.

2. **[high] Attachment and project mentions have no defined disclosure boundary.**  
   **Reference:** Composer: “attach files or project folders”; Context panel: “attached files, selected project.”  
   **Why it matters:** It is unclear whether selecting a project sends its contents, merely sets `cwd`, or permits later reads. Folder attachments lack exclusions, size limits, snapshot semantics, and removal behavior. This leaves the explicit-content-sharing promise in 11 ambiguous.  
   **Concrete fix:** Distinguish working directory, attached content, and readable scope. Preview the files, exclusions, total size, and receiving provider before submission; apply secret exclusions and resolved-path checks. Record the exact attachment snapshot used by each run.

3. **[high] Automatic titles silently introduce another model recipient.**  
   **Reference:** Behavior rules: “Titles are auto-generated by the cheapest connected model after the first exchange.”  
   **Why it matters:** A conversation intentionally sent to one provider could be forwarded to another without a visible choice. “Cheapest” is also undefined for subscription capacity, and title generation consumes another run.  
   **Concrete fix:** Default to a local title derived from the first user message. Make model-generated titles optional, use the conversation’s chosen provider, specify the minimal excerpt sent, and keep title failures independent of chat delivery.

4. **[high] Rich message rendering lacks an untrusted-content contract.**  
   **Reference:** Messages: “markdown, code blocks with copy, tables, collapsible thinking, tool-call cards.”  
   **Why it matters:** Model and tool output can contain hostile HTML, links, remote image URLs, or misleading action-like content. Local storage does not prevent browser execution or network disclosure during rendering.  
   **Concrete fix:** Require sanitized Markdown with raw HTML disabled, safe URL schemes, and blocked remote media by default. Render tool cards from validated structured events; generated text must never create executable approval controls. Show thinking only when the adapter explicitly supplies displayable content.

5. **[high] “Replay as plain messages” leaves cross-model history and disclosure undefined.**  
   **Reference:** Behavior rules: “Switching model mid-thread is allowed; history is replayed as plain messages.”  
   **Why it matters:** The thread may contain attachments, tool results, agent replies, thinking, and cancelled output. Flattening these can lose attribution, replay incomplete answers as complete, exceed context limits, and send previous private material to another provider.  
   **Concrete fix:** Define a canonical replay format that preserves roles and provenance, excludes private/internal content, labels partial output, and specifies attachment handling. Add a context-budget policy and a visible disclosure summary when changing providers; do not silently truncate history.

6. **[high] Streaming and cancellation lack a recoverable run contract.**  
   **Reference:** “Streaming with cancel. Partial output is kept on cancel”; API sketch.  
   **Why it matters:** The sketch does not explain duplicate submissions, reconnecting after refresh, recovering missed events, or cancellation while a tool is running. This leaves 01’s restart-reliability promise untestable from Chat.  
   **Concrete fix:** Define idempotent submission, stable message/run IDs, ordered resumable events, and a history/run retrieval path. Specify queued, running, awaiting approval, cancelling, cancelled, failed, and completed states. Preserve drafts and partial output; distinguish stopping generation from reversing completed tool actions.

7. **[med] The feature list conceals a substantial phase mismatch.**  
   **Reference:** Compare mode “phase 3”; `/task`, `/card`, `/hermes`, agent mentions, project folders; Phase 1 acceptance criteria.  
   **Why it matters:** Roadmap 13 assigns compare mode to Phase 4, scheduling to Phase 2, agents/Kanban to Phase 3, and indexing to Phase 4. Most features here have no phase, so a small Phase 1 chat milestone can expand into several later systems.  
   **Concrete fix:** Assign every feature a delivery phase and reconcile compare mode with 13. Explicitly distinguish basic manual attachments/project selection from indexed browsing. Extend Phase 1 acceptance to cover Codex, persisted history, cancellation, reconnect recovery, and routing fallback.

8. **[med] Provider, effort, and fallback behavior contradict the promised send states.**  
   **Reference:** Model picker and effort picker; acceptance: a logged-out provider means the composer “cannot send.”  
   **Why it matters:** Routing spec 03 permits fallback when the selected provider needs login. The UI therefore has two competing behaviors. It also does not define what happens when switching models invalidates the selected effort.  
   **Concrete fix:** Define when fallback is enabled, how the effective destination is disclosed, and when sending is blocked. Specify a supported effort default on model changes and distinguish requested settings from effective settings in the message/run record. Keep Connect reachable outside disabled options.

9. **[med] Retry and branch have no conversation semantics.**  
   **Reference:** Messages: “retry with another model, branch from this message.”  
   **Why it matters:** There is no definition of whether retry replaces an answer, creates a sibling, or re-executes tools. Branch relationships are absent from data model 02, so implementations could discard audit history or duplicate actions.  
   **Concrete fix:** Preserve the original answer/run, define which preceding messages and attachments a retry receives, and represent branches explicitly. Require fresh authorization for repeated side effects; show the active branch and provide a clear return path.

10. **[med] The column layout has no minimum readable thread width.**  
    **Reference:** Layout: conversation list, thread, composer, collapsible Context panel; “matches mockup.”  
    **Why it matters:** The Stitch prompt specifies a 260px conversation list and 300px Context panel, while 14 specifies 360–420px drawers. With the global rail and gutters, intermediate desktop widths can leave very little room for prose, code, or the effort control. The below-900px sheet rule alone does not resolve this.  
    **Concrete fix:** Set a minimum thread width and collapse Context, then the conversation list, when that width cannot be maintained. Specify panel defaults, independent scrolling, composer visibility with the software keyboard open, and horizontal scrolling confined to wide code/tables.

11. **[med] Message hierarchy, typography, and spacing are unspecified.**  
    **Reference:** Messages combines routing metadata, prose, thinking, tool cards, and four secondary actions.  
    **Why it matters:** Nothing establishes what should dominate or how dense repeated messages should become. The incumbent CSS uses 70%-width bubbles and 10px gaps; extending that directly could compress long answers while producing persistent metadata and action clutter.  
    **Concrete fix:** Define a chat-specific reading hierarchy: prose first, compact muted attribution, secondary actions in a keyboard-accessible menu, and collapsed thinking/tool details. Specify approximately 16px prose with 1.5–1.6 line height, a 65–75ch measure within 14’s width cap, and distinct spacing for paragraphs, message groups, and turns.

12. **[med] Glass contrast requirements are not translated into chat states.**  
    **Reference:** “Layout (matches mockup)” and Messages; inherited tokens in 14.  
    **Why it matters:** The shared 4.5:1 rule does not specify the composite backgrounds beneath message text, menus, selections, or focus indicators. If `#E7E8EC` text is placed on solid violet `#8B5CF6`, contrast is only **3.46:1**. Blur makes checking the base background alone insufficient.  
    **Concrete fix:** Require contrast checks over the brightest permitted atmosphere and every selected/hover state. Define sufficiently opaque text-bearing surfaces and opaque fallbacks for unsupported blur and increased-contrast preferences. A possible alternative accent is ice blue `#7DD3FC`, which separates primary actions from teal health states: dark `#0B0C0F` labels on that solid fill achieve **11.73:1**; light labels would fail at **1.36:1**.

13. **[med] Keyboard, streaming accessibility, and motion behavior are missing.**  
    **Reference:** Composer’s Enter shortcuts, picker popover, collapsible panels, and streaming.  
    **Why it matters:** Global guidance in 14 asks each spec to list keyboard behavior, but this one does not cover picker navigation, focus restoration, screen-reader updates, or IME composition. Unspecified autoscroll can repeatedly pull readers away from earlier messages.  
    **Concrete fix:** Define keyboard navigation and Escape behavior for pickers, mentions, commands, and sheets; label selected effort and disabled reasons. Suppress Enter-to-send during IME composition. Announce streaming in batches, follow output only when already at the bottom, and otherwise offer “Jump to latest.” Specify brief state transitions, reduced-motion behavior, and no repeated message entrance animations.
