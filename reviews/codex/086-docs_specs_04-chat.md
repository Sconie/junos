1. **[high] Tool toggles do not define an enforceable permission boundary.**  
   **Reference:** Features, “tool toggles (Files, Web, Hermes, Tasks)”; Behavior rules, “always behind the approval policy in 12.”  
   **Why it matters:** Models run through official CLI clients (03), which may expose their own tools independently of the daemon’s small tool set. Setting `cwd` scopes execution location; it does not establish file-access permissions. The spec never requires adapters to enforce the displayed toggles or explains what happens when they cannot.  
   **Concrete fix:** Require adapters to enforce the effective allowlist and approval policy across native and daemon tools. Disable unsupported tool configurations with an explanation. Show pending approvals inline with the exact action, Approve/Deny, and timeout state. Gate tool-enabled chat on this enforcement.

2. **[high] Cross-provider disclosure happens without a defined privacy boundary.**  
   **Reference:** Behavior rules, “history is replayed as plain messages” and “Titles are auto-generated by the cheapest connected model.”  
   **Why it matters:** Switching providers, automatic fallback (03), and title generation can transmit conversation content to additional providers. “Conversations are stored locally” describes storage, but does not explain these outbound transfers. “Cheapest” also lacks a defined meaning for subscription routes.  
   **Concrete fix:** Define permitted providers per conversation, including fallback and title generation. Show the destination before the first transfer to a new provider. Generate titles locally or through the conversation’s permitted route, with manual titles as a fallback.

3. **[high] Folder attachment and mention semantics are dangerously ambiguous.**  
   **Reference:** Composer, “attach files or project folders”; Context panel, “selected project (sets `cwd`).”  
   **Why it matters:** Attaching a folder could mean sending every file, granting tool access, or adding only a project reference. These have different privacy and context-size consequences. Spec 11 excludes secrets and ignored paths, but 04 does not establish how those protections apply to direct attachments and `@` mentions.  
   **Concrete fix:** Distinguish **attach content**, **select working directory**, and **grant file access**. Resolve attachments in the daemon against allowed roots, exclusions, symlink boundaries, and size limits. Show a removable manifest with file count, bytes, estimated tokens, and excluded items before submission.

4. **[high] Model output has no rendering security contract.**  
   **Reference:** Messages, “markdown, code blocks … tables … tool-call cards … ‘save to file’.”  
   **Why it matters:** Conversation content and tool output are untrusted. The spec leaves raw HTML, executable URL schemes, remote images, and output-derived file paths unspecified. Remote images can disclose that a conversation was opened; unsafe rendering can compromise the local UI.  
   **Concrete fix:** Require sanitized markdown, disabled raw HTML, allowlisted link protocols, and blocked remote images until explicitly loaded. Treat tool arguments as inert text. Make “save to file” use a user-selected, daemon-validated destination with overwrite handling.

5. **[high] Streaming defines cancellation but omits recovery and duplicate prevention.**  
   **Reference:** “Streaming with cancel. Partial output is kept on cancel”; API sketch; Phase 1 acceptance criteria.  
   **Why it matters:** There is no behavior for refresh, SSE disconnection, daemon restart, double submission, provider failure, or cancellation racing completion. This falls short of 01’s requirement that runs resume or fail cleanly. Repeated requests could create duplicate runs or repeat tool effects.  
   **Concrete fix:** Return stable message/run IDs, accept an idempotency key, and define how clients reload persisted output and resume events. Specify queued/running/waiting-approval/completed/failed/cancelled states. Keep partial responses visibly incomplete, preserve unsent drafts, and require deliberate retry after uncertain execution.

6. **[med] “Plain messages” cannot fully specify switching, retrying, or branching.**  
   **Reference:** Behavior rules, “history is replayed as plain messages”; Messages, “retry with another model, branch from this message.”  
   **Why it matters:** The thread also contains attachments, thinking, tool calls, and agent results. The spec does not say which become replayed context, how oversized histories are handled, or whether retry can repeat side effects. The schema in 02 has no explicit branch ancestry or response-variant relationship.  
   **Concrete fix:** Define a canonical replay format, preserving roles and attachment provenance while excluding private thinking and treating tool output as untrusted data. Specify context-overflow handling. Make retries create linked response variants, branches capture an immutable prefix, and completed tool actions remain unrepeated unless separately requested.

7. **[med] Phase boundaries contradict the roadmap and leave acceptance too narrow.**  
   **Reference:** Features; “Compare mode (phase 3)”; Phase 1 acceptance criteria.  
   **Why it matters:** Tasks belong to Phase 2, agents/Kanban to Phase 3, and indexing/compare to Phase 4 in 13. Most features here have no phase label, while compare explicitly disagrees. Phase 1 acceptance tests only Claude even though the roadmap requires Claude and Codex.  
   **Concrete fix:** Add a feature-to-phase table inside 04. Reconcile compare with Phase 4 and distinguish basic direct attachments from indexed mentions. Expand Phase 1 acceptance to both adapters, persisted history, valid effort selection, fallback behavior, cancellation, recovery, and enforced permissions for any enabled tools.

8. **[med] Routing and model identity become misleading after switches or fallback.**  
   **Reference:** Layout, “provider icon each”; Messages, model/effort/route header; logged-out acceptance criterion.  
   **Why it matters:** A conversation can contain multiple providers, so one provider icon has no defined meaning. Spec 03 automatically falls back when login expires, whereas 04 says the composer cannot send. Requested effort may also differ from the effort supported by a fallback model.  
   **Concrete fix:** Define whether the list icon represents the last responder or a mixed-provider thread. Distinguish requested settings from the actual responding model, effective effort, route, and fallback reason. Specify when fallback proceeds and when sending is blocked; explain unsupported effort levels rather than merely greying them out.

9. **[med] Panel sizing can squeeze out the conversation’s reading space.**  
   **Reference:** Layout, “matches mockup”; left list and right Context panel.  
   **Why it matters:** The Stitch prompt uses 260px and 300px side panels, while 14 specifies 360–420px drawers. With the global rail and gutters, both interpretations can leave a narrow thread at ordinary laptop widths. The 760px readable-width maximum in 14 does not establish a minimum or collapse priority.  
   **Concrete fix:** State authoritative chat widths and collapse order. Keep Context closed by default; collapse it, then the conversation list, before compromising the thread. Reference 14’s below-900px sheets explicitly. Require usable layouts at 1024px, 390px, and 200% zoom, with wide code/tables scrolling inside their own containers.

10. **[med] Message hierarchy, spacing, and typography are left to implementation guesswork.**  
    **Reference:** Messages feature list and Layout section.  
    **Why it matters:** Every message can carry routing metadata, thinking, tool cards, and four secondary actions, but their prominence is unspecified. The existing shell uses 70%-width bubbles (`src/index.css:82`), which could unnecessarily constrain long assistant answers if retained.  
    **Concrete fix:** Specify a reading hierarchy: answer text first, compact metadata second, secondary actions in a keyboard-accessible menu. Start with 16px message text, approximately 1.6 line height, 13–14px metadata/code, and consistent 8/16/24px spacing. Use the available readable width for assistant prose; collapse detailed tool output and reasoning summaries by default.

11. **[med] Glass legibility requirements are not translated into chat-specific acceptance checks.**  
    **Reference:** Layout and Messages; inherited tokens and accessibility rules in 14.  
    **Why it matters:** Spec 14 already requires contrast and fallbacks, but 04 does not cover overlapping picker/composer glass, syntax highlighting, attachment chips, or muted metadata over glow. The proposed `#E7E8EC` text on solid violet `#8B5CF6` is only **3.46:1**, below the stated 4.5:1 text requirement if used for normal-size selected controls.  
    **Concrete fix:** Define tested foreground/background pairs for every chat state, including the brightest glow and overlapping surfaces. Give dense popovers a reliable surface fill. A possible accent is **mist blue `#A8C7FA`**: it provides **9.80:1** on an opaque `#1C1D20` fallback, while `#0B0C0F` labels on blue provide **11.38:1**. This supports readable controls while reserving teal for healthy/running states. Test actual translucent composites separately.

12. **[med] Keyboard, scrolling, and motion behavior are missing from the primary interaction.**  
    **Reference:** Composer, “Enter to send”; streaming and collapsible panels.  
    **Why it matters:** Enter handling can submit during IME composition or interfere with command suggestions. Streaming can pull readers away from older messages or overwhelm screen-reader announcements. Spec 14 requests keyboard-first behavior and reduced motion, but 04 supplies no interaction contract.  
    **Concrete fix:** Suppress submission during composition; let Enter select an open suggestion and Escape dismiss it. Define picker/list keyboard navigation and focus restoration. Follow streaming output only while the reader is at the bottom, otherwise show “Jump to latest.” Announce status changes without reading every token. Under reduced motion, remove animated reveals, smooth scrolling, and pulsing effects; provide an opaque chat presentation for contrast/transparency preferences.
