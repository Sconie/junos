1. **[high] Tool toggles do not define an enforceable permission boundary.**  
   **Reference:** “selected project (sets `cwd` for CLI-backed models)” and “always behind the approval policy in 12” ([lines 15–22](docs/specs/04-chat.md#L15)).  
   **Why it matters:** A working directory does not restrict filesystem access. The spec describes daemon tools but does not explain how provider CLIs’ own file, shell, or network tools obey those toggles and approvals. A visually disabled tool could remain operational.  
   **Fix:** Require adapters to enforce the effective tool allowlist and approval policy, including native CLI tools. Disable capabilities whose enforcement cannot be verified. Show effective permissions beside the composer; changing projects must invalidate permissions scoped to the previous project.

2. **[high] Automatic model selection can disclose conversation content to another provider.**  
   **Reference:** “Titles are auto-generated by the cheapest connected model” and “history is replayed as plain messages” ([lines 21–23](docs/specs/04-chat.md#L21)).  
   **Why it matters:** Title generation can send private text to a provider Jonas never selected. Switching models and the fallback behavior in [03](docs/specs/03-connections-and-routing.md#L33) can also transfer previous messages and attachments. “Stored locally” does not explain these outbound disclosures.  
   **Fix:** Generate titles locally or through the selected provider by default. Define which history and attachments accompany model changes, and require explicit opt-in before automatic cross-provider fallback. Show the destination before sending and record the actual provider afterward.

3. **[high] Folder attachments and mentions have no bounded disclosure contract.**  
   **Reference:** “attach files or project folders” and “`@` to mention a file, project, or agent” ([line 10](docs/specs/04-chat.md#L10)).  
   **Why it matters:** It is unclear whether selecting a project sets `cwd`, uploads its contents, or authorizes future reads. Recursive folders can include secrets, huge files, or links outside the permitted root. [11](docs/specs/11-files-and-projects.md#L25) promises explicit attachment and default secret exclusions, but this interaction does not establish their application.  
   **Fix:** Distinguish project selection, attachment, and agent handoff. Before sending a folder, show a removable file manifest with exclusions, sizes, and destination. Enforce canonical-path allowlisting, link handling, secret exclusions, and file/count/byte limits in the daemon.

4. **[high] Rich message rendering lacks an untrusted-content policy.**  
   **Reference:** “markdown, code blocks with copy, tables … tool-call cards” ([line 13](docs/specs/04-chat.md#L13)).  
   **Why it matters:** Model and tool output will appear inside an authenticated local application. Active HTML, unsafe URL schemes, and remote images can introduce script execution or unintended network requests. Approval-looking content could also be confused with trusted application controls.  
   **Fix:** Require sanitized Markdown with raw HTML disabled, restricted link schemes, and remote media blocked by default. Render tool output as inert content. Construct approval controls exclusively from trusted daemon events, with clear separation from assistant prose.

5. **[high] Cancellation and stream recovery are underspecified for runs that can act.**  
   **Reference:** “Streaming with cancel. Partial output is kept on cancel” and the [API sketch](docs/specs/04-chat.md#L25).  
   **Why it matters:** Keeping partial text says nothing about whether execution stopped. A dropped connection or retried submission could start a duplicate run or repeat tool actions. The architecture already requires clean recovery after daemon restarts.  
   **Fix:** Specify durable message/run IDs, idempotent submission, ordered resumable events, and history retrieval. Distinguish reconnecting from rerunning. Show `Stopping` until cancellation is acknowledged, retain a clearly marked partial response, and preserve an audit of actions already completed.

6. **[med] The feature list obscures the Phase 1 boundary and contradicts the compare-mode roadmap.**  
   **Reference:** Agent mentions, scheduling commands, Kanban actions, branching, attachments, and “Compare mode (phase 3)” ([lines 10–17](docs/specs/04-chat.md#L10)).  
   **Why it matters:** These read as one deliverable, although the [roadmap](docs/specs/13-roadmap.md#L11) introduces automation in Phase 2, agents and Kanban in Phase 3, and compare mode in Phase 4. Phase 1 acceptance also omits the Codex path required by that roadmap.  
   **Fix:** Assign every feature a phase and prerequisite. Align compare mode with one authoritative phase. Keep Phase 1 acceptance focused on Claude/Codex, persistence, valid model/effort combinations, routing, and reliable streaming.

7. **[med] Retry, branching, and model switching lack conversation semantics.**  
   **Reference:** “retry with another model, branch from this message” and “history is replayed as plain messages” ([lines 13–21](docs/specs/04-chat.md#L13)).  
   **Why it matters:** The spec does not say whether retry replaces an answer, which branch becomes active, or whether failed partial output, thinking, and tool results enter the next prompt. The [data model](docs/specs/02-data-model.md#L11) has no explicit branch or revision relationships.  
   **Fix:** Define retries as preserved sibling attempts and branches as histories ending at a selected message. Specify role-preserving history conversion, attachment handling, and exclusions for hidden thinking and provider-specific tool payloads. Revalidate effort when changing models.

8. **[med] A token estimate has no overflow behavior.**  
   **Reference:** “Context panel … token estimate” ([line 15](docs/specs/04-chat.md#L15)).  
   **Why it matters:** Long threads and folders can exceed the selected model’s capacity. Without a policy, implementations may silently omit context, fail after submission, or imply precision that adapters cannot provide.  
   **Fix:** Label estimates as approximate, account for attachments and output reserve, and recalculate after model changes. Before exceeding capacity, offer explicit context removal or a disclosed summarization step. Never silently truncate history.

9. **[med] The three-column layout needs collapse rules above the mobile breakpoint.**  
   **Reference:** “Left: conversation list … Center: thread … Right … Context panel” ([line 7](docs/specs/04-chat.md#L7)).  
   **Why it matters:** The mockup specifies a 260px list; [14](docs/specs/14-ui-system.md#L24) specifies a 64px rail and 360–420px drawers. At 1024px, that leaves only 280–340px for the thread before gutters, while the sheet breakpoint is below 900px.  
   **Fix:** Define a minimum usable thread width and collapse Context first, then the conversation list, whenever that width cannot be maintained. Specify composer behavior with the mobile keyboard, safe areas, zoom, and narrow viewports.

10. **[med] Message controls and metadata have no hierarchy or density budget.**  
    **Reference:** The model/effort/route header plus thinking, tools, retry, branch, Kanban, and save actions ([line 13](docs/specs/04-chat.md#L13)).  
    **Why it matters:** Giving every feature equal prominence would surround each answer with competing chrome. Provider icons on conversations also become ambiguous once models can change mid-thread.  
    **Fix:** Make the answer the primary reading surface, provenance a quiet secondary line, and utility actions an accessible overflow menu. Collapse thinking and completed tool details by default; keep errors and pending approvals visible. Define conversation icons as “last responder” or use a stable conversation/agent identity.

11. **[med] Typography and spacing are too unspecified to protect long-form reading.**  
    **Reference:** “markdown … code blocks … tables” and “matches mockup” ([lines 6–13](docs/specs/04-chat.md#L6)).  
    **Why it matters:** The shared 760px width limit does not establish comfortable line length, paragraph rhythm, or code/table handling. Existing `.bubble` styles use a percentage width, which can make content unnecessarily narrow when panels are open.  
    **Fix:** Define chat-specific tokens: approximately 16px body text at 1.5–1.6 line height, a 60–75-character prose measure, readable 12–13px metadata, and consistent paragraph/message gaps. Align assistant prose and composer edges; scroll code and wide tables within their own containers.

12. **[med] Glass contrast and accent usage need explicit component pairings.**  
    **Reference:** “matches mockup” and “greyed” effort options ([lines 6–12](docs/specs/04-chat.md#L6)); inherited tokens in [14](docs/specs/14-ui-system.md#L5).  
    **Why it matters:** A general contrast rule does not specify which text sits on which glass or accent surface. For example, `#E7E8EC` on solid violet `#8B5CF6` is **3.46:1**; white is **4.23:1**. Neither reaches the stated 4.5:1 target for normal text. These are calculated solid-color pairs, not rendered glass measurements.  
    **Fix:** Specify text/fill/focus pairings and validate the brightest permitted glow behind each glass surface. A viable alternative is the source’s cornflower `#7C9CFF`: **7.50:1** against `#0B0C0F`, and **6.94:1** against `#14161B`. It offers a readable action accent while keeping teal for health. Use dark ink on filled blue controls; white achieves only **2.61:1**. Require an opaque high-contrast/user-selected fallback as well as unsupported-blur fallback.

13. **[med] Keyboard and assistive-technology behavior is missing from the interaction contract.**  
    **Reference:** Enter-to-send, model popover, segmented effort control, slash commands, and mentions ([lines 10–17](docs/specs/04-chat.md#L10)).  
    **Why it matters:** Enter can accidentally submit during IME composition or while selecting a mention. “Greyed” options do not explain unavailable effort levels, and disabled provider rows can make their Connect action unreachable.  
    **Fix:** Suppress submission during composition and autocomplete selection. Define arrow-key selection, Escape dismissal, focus return, accessible names, and selected/disabled semantics. Keep Connect independently operable. Announce run status and completion without reading every streamed token aloud.

14. **[med] Streaming has no scroll, layout-stability, or motion policy.**  
    **Reference:** “Streaming with cancel” and expandable thinking/tool cards ([lines 13–14](docs/specs/04-chat.md#L13)).  
    **Why it matters:** Forced autoscroll can pull Jonas away from text he is reading; streamed Markdown and expanding cards can move content underneath him. Shared reduced-motion guidance does not define these chat-specific behaviors.  
    **Fix:** Follow new output only while the reader is near the bottom; otherwise show a “Jump to latest” control. Preserve position when loading history or expanding details. Batch visual updates, avoid per-token entrance effects, and disable smooth scrolling and animated progress effects under reduced motion.
